# Findings

## MEDIUM — docs/usability — `src/tools.ts:254`, `src/tools.ts:277` (and `test/editMessage.test.ts:157,159`)
The schema and description invite `content` + `stream_id` in one call, which Zulip always rejects. `https://zulip.com/api/update-message` states verbatim, in both the `content` and `stream_id` parameter descriptions: *"Note that a message's content and channel cannot be changed at the same time, so sending both `content` and `stream_id` parameters will throw an error."* The description only says "Provide at least one of content, topic, or stream_id", so a model doing "move this message and fix its typo" issues one call and gets a server error with no hint that two calls are required.

Failure scenario: `edit_message {message_id: 42, content: "fixed", stream_id: 17}` → `src/tool-runtime.ts:727` encodes both → Zulip 400. Worse, `test/editMessage.test.ts:157` (`'content and stream'`) and `:159` (`'all fields'`) enshrine this combination as a supported encoding; they pass because the fixture at `test/editMessage.test.ts:13` is a stub that echoes success for any body, so these two cases are tests that pass without exercising reality.

Fix direction: add one clause to the `edit_message` description and/or the `stream_id` description — "a stream move cannot be combined with a content edit; send them as two calls". Rejecting the pair locally is also defensible (it is Zulip's own rule, not extra strictness), but documenting it is the minimum. Relabel or drop the two misleading test cases.

## MEDIUM — docs/usability — `src/tools.ts:254`, `src/tools.ts:272`
"Omit it for Zulip's default" hides which default. Zulip documents `propagate_mode` *"Defaults to `"change_one"`"* — so a bare `{message_id, topic}` rename moves **only that one message** out of the topic, splitting the topic in two rather than renaming it. That is the inverse of the task's stated purpose (servo-skull renaming/moving topics), and the caller gets `result: success` with no signal that the rest of the topic stayed behind.

Failure scenario: model is asked "rename this topic to X", sends `{message_id: 42, topic: "X"}`, Zulip returns success, one message is now in topic X and the other fifty remain under the old name.

Fix direction: name the default in the description, e.g. "Zulip defaults to `change_one` (this message only); pass `change_all` to rename/move the whole topic, `change_later` for this message and later ones." The code is right to omit the field; only the description needs to stop being coy. (Consider making the `propagate_mode` property description lead with the default.)

## LOW — docs — `src/tools.ts:272`
Zulip also documents *"Only the default value of `"change_one"` is valid when editing only the content of a message."* The implementation forwards `propagate_mode` with content-only edits (`src/tool-runtime.ts:727`), so `{content, propagate_mode: "change_all"}` is a server error. The description's "With topic or stream_id:" prefix mostly covers this; one explicit "ignored/invalid for content-only edits" clause would close it. Error surfaces truthfully either way.

## LOW — correctness (cosmetic) — `src/tool-runtime.ts:708-718` vs `:719`
`message_id` is validated *after* the new field checks, so `edit_message {}` reports "At least one of content, topic, or stream_id is required" rather than the missing `message_id`. Pre-existing ordering trait (content was also checked before `message_id` at base); harmless, but moving the `message_id` guard first gives the caller the more actionable error.

## Recommendation (not a finding) — `send_notification_to_old_thread` / `send_notification_to_new_thread`
Do **not** expose them in this PR. Zulip's defaults are `send_notification_to_old_thread: false` and `send_notification_to_new_thread: true`; omitting both (as this commit does) is the correct "realm decides" behaviour and matches the ask. The one real argument for exposing them later: this server monitors channels, so the automated "moved here" notice generated by a bot-initiated move arrives back as a new message event and can add noise to the bot's own topics. If that becomes a problem, add them as optional booleans with no local default, stringified the same way as the existing fields — a separate, smaller change. Not an acceptance gap.

# Unmet Criteria / test gaps

Acceptance criteria are all met (optional `topic`/`propagate_mode`/`stream_id`; content optional when topic/stream given; backward compatible; tests). The upstream PR is an owner action, out of scope here.

Test gaps:
1. **The stub fixture accepts any body**, so no test can distinguish a legal Zulip request from an illegal one. This is what lets `'content and stream'` and `'all fields'` (`test/editMessage.test.ts:157,159`) look like supported features. A stub that mirrors Zulip's two documented mutual-exclusions (content+stream_id; non-`change_one` with content-only) would turn those two cases into the error assertions they should be.
2. **No test pins the tool description**, so the two MEDIUM findings are invisible to CI. A test asserting the description mentions `change_one` as the default would lock in finding #2's fix.
3. **No end-to-end move test** through the event loop: nothing asserts that a bot-initiated move produces the `update_message`/`orig_subject` event the handler at `src/platforms/zulip-events.ts:404-407` expects, or that monitored-channel state survives a cross-stream move. Requires a live realm; out of scope, noted as risk.

# Residual Risk

- **No live realm.** Every Zulip-side rule (permissions, `change_all` time limits, empty-topic realm setting, the content+stream_id rejection) is asserted from documentation and a loopback stub only. The two MEDIUM findings are precisely the places where documentation and stub disagree about what a real server accepts.
- **Post-move local state.** After a successful cross-stream move the bot's cached/monitored state for the moved messages is updated only via the incoming `update_message` event; if that event is missed or filtered, the bot's view of where the message lives goes stale. Pre-existing for moves made by others — this change makes the bot able to trigger it itself, so the exposure is new even though the code is not.
- **`change_all` is destructive-ish and now one tool call away.** A model with the `comms` tool class can move an entire topic; the only brake is realm policy (by design, per the brief). Finding #2's fix matters here in both directions — a model that learns `change_all` will use it.
- 3 pre-existing npm audit vulnerabilities (1 low, 2 high) at both base and head; dependencies unchanged, out of scope.
